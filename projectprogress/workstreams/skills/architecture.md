# Skills architecture

Implemented: senai/skills/registry.py; public exports in senai/skills/__init__.py.

Registry(root) is an explicit isolated registry; callers should choose this worktree's outputs/. import_local(directory) snapshots regular files, validates SKILL.md, copies into a random registry-owned directory and activates one name in a SQLite transaction. Failed validation does not activate anything. Ordinary write/transaction failures clean up staged content; a process crash may leave inactive orphan directories, never intentionally selected entries. SQLite commits retain name, version, description, source absolute path, package digest and content directory. Imports never execute code.

list()/select(names) verify the stored full-package digest before returning frozen Skill records containing instructions and SKILL.md path. execute() is only an injected context boundary. Selection is explicit; no semantic matching, global discovery, native installation or replacement Codex executor.

Supported compatibility: deliberately restricted SKILL.md-style UTF-8 frontmatter. Opening/closing --- lines; required single-line name and description, optional version (default 1). Names are lowercase alphanumeric hyphen-separated, at most 64 characters; versions are bounded alphanumeric/dot/underscore/hyphen tokens. Simple quoted scalars supported. Unknown/duplicate keys, multiline/nested YAML and empty instructions rejected. This is not full YAML or a claim of universal Codex/Hermes package compatibility. Max 256 files, 1 MiB/file, 8 MiB/package. Auxiliary files are preserved. All source/content symlinks and archives are rejected. Duplicate names require a future explicit revision API rather than overwrite.

Trust boundary: instruction text remains untrusted content; syntax validation and hashes do not prove safe instructions. Caller controls selection/execution. Registry/source directories must not be concurrently modified by untrusted processes: filesystem snapshotting is not an OS isolation boundary or a defense against hostile file-replacement races. No evidence-based revision claims are made yet.

No third-party dependencies, downloaded references, authored reusable Codex skill, model calls, or sibling-feature imports used in this milestone. Remaining work is recorded in current task.md.

## Learning architecture and current step

Planned project layout: outputs/skills/registry.sqlite3 plus registry-owned package snapshot folders. Keep the existing package paths and import_local/list/select/execute contracts compatible. The SQLite outcomes table now stores immutable ID, skill name/version/digest, request, result, checks JSON, correction, derived status and UTC timestamp. outcomes(name) lists them in insertion order. No write happens merely by importing the Python package.

Check(name, passed, evidence) is a frozen record supplied by a trusted adapter. record_outcome(name, *, digest, request, result, checks=(), correction="") validates bounded text, boolean check results and active content identity. No checks means unverified; all checks passing means passed; any failing check means failed. These labels describe supplied checks, not universal task correctness or authenticated evidence. Recording does not change selected instructions. No raw production transcript, credentials, or live state is gathered automatically.

Future tables: immutable revision candidates with base digest and outcome links, regression evidence, active revision pointer and activation/rollback audit history. Future loop: select -> existing execution -> observed checks -> append outcome -> Codex-generated proposal -> isolated regression checks -> activate -> reuse. No model weights are changed. The coordinator owns insertion of shared post-execution hooks; this feature supplies injected interfaces only.

Research sources read 2026-11-09: https://hermes-agent.nousresearch.com/docs/user-guide/features/skills ; https://hermes-agent.nousresearch.com/docs/user-guide/features/memory ; https://agentskills.io/specification . Hermes uses procedural skills, progressive disclosure and agent-managed/background revisions; our proposed explicit regression gate and immutable history are project design choices, not a claim to duplicate Hermes implementation. Metadata-only catalog/resource loading and broader frontmatter compatibility remain future work.

## Implemented revision proposal step

propose_revision(name, *, document, outcome_ids, reason) accepts a complete replacement SKILL.md string and returns frozen Revision. It preserves every supporting file from the current skill package. Candidate metadata must keep the same name, use a distinct bounded version, and change instruction text. Version ordering is not inferred; duplicate versions for a skill are rejected.

The additive revisions table stores ID, skill name/version, base digest, candidate digest, original source, ordered outcome-ID links, reason, package directory and UTC timestamp. A UNIQUE(skill_name, version) constraint reserves versions. Proposal insertion is transactional with an active-base recheck; ordinary failures remove staged package folders. As with imports, a hard process crash can leave an inactive orphan folder. No selection pointer changes.

Evidence must be nonempty, unique and already recorded as passed/failed for this exact skill digest; unverified prose and other-skill evidence cannot support proposals. This is validation of trusted-adapter records, not independent authentication of evidence. No LLM drafting occurs in this API. revisions(name) returns proposals in insertion order after verifying full candidate content hashes and metadata. select/execute continue to expose only the original active skill.

Revision packages are currently instruction-only changes: support files cannot be added/edited through proposal creation. Candidate regression validation, activation, rollback and audit events remain pending. Revision is publicly exported from senai.skills. Existing skills/outcomes schemas and public signatures are unchanged.

## Implemented regression validation step

validate_revision(revision_id, *, validator) calls trusted validator(base, candidate, outcomes) and returns frozen Validation. The inputs are exact base Skill, proposed Revision and ordered tuple of linked Outcome records. Return an iterable of Check records with observed evidence. At least one check is required; callers should cover both old successful behavior and the corrected failure. Selecting meaningful cases is the caller's responsibility; a passing label is not universal improvement proof.

The additive validations table retains ID, revision ID, base/candidate digests, checks JSON, passed/failed/error status, sanitized error description and UTC timestamp. Failed checks are recorded as failed. Empty/malformed returns and ordinary checker exceptions are recorded as error with no raw exception message. KeyboardInterrupt/SystemExit propagate. validations(revision_id) retains every attempt in insertion order; a future activation gate must use the latest attempt, never an earlier pass after a failure.

Hashes are checked before and after the callback; changing candidate/base bytes prevents saving a pass. Active base is rechecked transactionally before result insertion. This is content identity verification, not OS sandboxing. The injected checker runs in the caller process and must supply its own isolated evaluation; no imported script is executed automatically. All proposals remain inactive, including passing ones. Shared Check validation is reused for outcomes and regression checks.

Public frozen Validation fields: id, revision_id, base_digest, candidate_digest, checks, status, error, created_at. Initialization creates the local validations table/index idempotently, leaving existing tables and records intact.

## Implemented activation and rollback step

activate_revision(revision_id) -> Skill explicitly moves the current skills row to the proposed package only if its base is still current and its latest validation attempt passed for the exact base and candidate digests. Full-package hashes and metadata are checked. Accepted-version insertion, active-row update and audit event commit atomically. A new failure/error after an earlier pass blocks activation. A sibling proposal becomes stale after another revision activates.

accepted_versions stores immutable accepted package references (name, version, description, source, digest, directory, accepted_at), unique per skill/version and skill/digest. Initial local imports are accepted baselines; syntax validation does not establish behavior. Existing registry active rows are backfilled idempotently on construction without losing previous outcomes/proposals/results. New proposals cannot reuse any accepted version identifier.

activation_history retains Activation(id, skill_name, action, from_digest, to_digest, revision_id, validation_id, reason, created_at). Actions are import, activate and rollback. history(name) reads audits even if current content is damaged. versions(name) lists accepted packages in first-acceptance order and verifies their contents; proposals are excluded.

rollback(name, *, digest, reason) restores an intact accepted package for the same skill, with a required rationale. Never-accepted candidates and current-version no-ops are rejected. It verifies only the destination bytes so that a damaged current package can be recovered. Rollback changes no file bytes and deletes no outcome/validation/history records. It can return to any previously accepted version (including a newer accepted version); this is restoration, not a new validation claim.

Revision.status now reports proposed, active or accepted according to recorded acceptance and current selection. Individual revision lookup validates only the requested package, allowing intact revisions/rollback to work despite unrelated damaged proposals. Registry select/execute retain their signatures and supply the currently active package.

No sandbox is introduced: registry directories remain trusted against hostile concurrent filesystem replacement. SQLite guards active-state updates but cannot provide an OS boundary around callbacks/files. No global Codex skills installed or shared execution/CLI code edited.

## Feature-local terminal interface

`python -m senai.skills --project EXISTING_PROJECT COMMAND` uses only that project's outputs/skills/ registry. Commands: import SOURCE_DIRECTORY, list, show NAME, context NAME REQUEST, outcomes NAME, versions NAME, history NAME, revisions NAME, validations REVISION_ID, activate REVISION_ID, rollback NAME --digest DIGEST --reason REASON, demo. Output is JSON; operational errors return 2 with a short stderr message. Help and listing a missing registry create no state. Import never executes code. Existing outputs symlinks are rejected through the stable workspace policy; global skills are untouched.

list emits active metadata without instruction text. show emits selected instructions, paths and provenance. context exports a request and one selected Skill through the existing injected executor seam; it deliberately makes no model call. Actual Codex use still needs an adapter. Candidate authoring and regression checking are currently Python APIs rather than user-supplied CLI check-result flags.

senai/skills/demo.py run_demo(project) creates a new retained outputs/skills-demo/run-*/ project, its fixture and its own outputs/skills registry. It records a synthetic failure, proposes instructions, injects a simulated passing regression, activates v2, restores v1 and reopens the registry. Mode and limitations are explicit in output. It never touches the normal project skill registry and never invokes a model/script. Repeated runs use separate folders. CLI entrypoint is senai/skills/__main__.py and main(argv=None, stdout=None, stderr=None) in cli.py. No shared console-entrypoint/package edits.

## Evidence-guided reviewer adapter

review_skill(registry, name, *, outcome_ids, reviewer) -> ReviewResult. reviewer(prompt: str) -> str JSON receives only the exact active SKILL.md and selected previously observed passed/failed Outcome records. No unverified, duplicate, missing or wrong-base evidence accepted. Budget: at most 100 selected IDs and 128 KiB total encoded prompt; oversize input is rejected before model use, not silently truncated. Caller must redact private data before recording evidence. No unrelated outcomes or filesystem paths are automatically added.

The prompt preserves user scope/permissions, asks for a narrow justified correction, forbids invented results and leaves supporting files unchanged. It allows no_change when evidence is insufficient. Target version is a fresh opaque r-UUID, not an inferred semantic increment. Response schema has exactly action, reason, document strings. Duplicate/unknown keys, malformed replies, unsupported metadata or wrong identity/version are rejected. A successful revise result passes through propose_revision and cannot create a passing validation. Model self-evaluation is not regression evidence. No-change results are returned to caller; no separate durable review-attempt log is added in this step. Revision rationale/evidence links persist for generated proposals.

ReviewResult(status, reason, revision) is frozen, with status proposed or no_change and revision possibly None. Active skill identity is rechecked after review so stale answers cannot be attached to a new base. Ordinary reviewer errors are converted to a generic SkillError without raw diagnostic text; there is no automatic retry or looping cost.

review_with_codex(registry, name, *, outcome_ids, project, model=None, executor=None) -> ReviewResult uses only the stable senai.codex.run_codex/ CodexOptions interfaces. Registry must be within the chosen real project outputs/. It creates a temporary .skills-review-* workspace/schema there, requests sandbox read-only, approval never, skip-git check and --output-schema, with an optional explicit model. No resume/--last is used for this separate one-shot review; shared bot-session mappings are untouched. executor can inject the existing run_codex signature for tests. Native config/auth/tool settings still apply; neither prompt text nor read-only mode independently isolates configured remote tools. No global skills/config/auth are modified by this module. Native CLI can retain its ordinary session history.

CLI review is opt-in and potentially a real authenticated model call. The offline demo remains synthetic and never starts it. Existing context command still only exports instructions. No shared execution trigger is installed.

Sources consulted for this step (2026-11-09): official https://learn.chatgpt.com/docs/non-interactive-mode and https://learn.chatgpt.com/docs/build-skills ; local system openai-docs/SKILL.md and skill-creator/SKILL.md. Applied narrow evidence-guided revisions and progressive-disclosure/scope guidance; these do not establish behavioral improvement. Installed parser flags were independently inspected, not assumed from online docs.

## Expanded metadata compatibility (supersedes initial restricted parser)

senai/skills/metadata.py reads UTF-8 SKILL.md frontmatter with PyYAML 6.0.3. YAML is parsed into nodes, then explicitly converted into inert strings/lists/mappings, without Python-object constructors. Explicit tags, anchors, aliases, merge keys and duplicate keys at any level are rejected. Limits: 16 KiB header, 1,024 YAML events and eight collection nesting levels. Name rules remain ASCII lowercase alphanumeric/hyphen, max 64. Required description is 1-1,024 characters; optional compatibility max 500, license/allowed-tools max 2,048. Unknown top-level fields rejected. Instruction body must be nonempty. Existing package size/hash limits still apply.

Supported top-level fields: name, description, version (legacy/Hermes extension), license, compatibility, allowed-tools, metadata. Version may come from metadata.version; if neither is supplied it defaults to 1. Both fields must agree when both exist. Numeric-looking scalars remain strings so legacy version: 1.0 and metadata.version retain lexical meaning. Plain YAML null is rejected where string/data is required. Nested string/list/map metadata is allowed as a Hermes extension; no secret/config setup or scripts run. This is broader SKILL.md-style compatibility, not full YAML or universal runtime compatibility. Legacy directory-name mismatch is still accepted to preserve existing imports, so strict Agent Skills folder/name conformance is not claimed.

Registry.metadata(name) returns a newly parsed dict of current validated declarations. CLI metadata NAME exposes it. allowed-tools is descriptive and never grants execution permissions. compatibility requirements are not automatically installed or evaluated. select(names, *, compatibility_check=None) optionally calls a trusted predicate(metadata) and requires literal True; execute(request, names, *, executor, compatibility_check=None) forwards it before execution. Omitting the predicate preserves existing explicit selection behavior.

Instruction revisions must preserve optional declarations, excluding the version value inside metadata. Description and instructions may change; version identity must change. Reviewer guidance now preserves supported optional fields and updates metadata.version if present. Tests exercise preservation through reviewer, regression validation and activation.

SkillError moved to errors.py and remains re-exported from registry/package, preserving existing imports. No schema or package snapshot rewriting. Previously accepted overlong/ambiguous metadata can now fail revalidation; this deliberately tightens format validation, and does not silently rewrite historical artifacts. Dependency is feature-local requirements-skills.txt until coordinator packaging integration.

Primary format references: https://agentskills.io/specification and https://hermes-agent.nousresearch.com/docs/user-guide/features/skills . Dependency release verified at https://pypi.org/project/PyYAML/6.0.3/ .

## Working live controlled demo

senai/skills/live_demo.py run_live_demo(project, *, executor=None, model=None, emit=None) -> dict. CLI demo --live opts into up to four installed Codex calls. Default demo stays offline-simulated. All fixture/source/registry/evaluation artifacts live in a unique outputs/skills-live-demo/run-* project. It neither scans nor modifies a normal project registry.

The CSV fixture initially converts textual identifiers to integers, deliberately losing leading zeros. `_evaluate` passes selected instructions and CSV batches through existing run_codex in read-only/approval-never mode with output-schema and no session resumption. A deterministic Python checker compares parsed JSON against expected stripped identifier strings and verifies batch count; it does not run downloaded or model-produced code. Prompts, raw JSON responses, schema and checks are retained per evaluation. Baseline failure is recorded as observed Outcome, then existing review_with_codex proposes a change. Existing validate_revision gates activation using actual candidate task output on regression batches. After acceptance, reopened registry supplies active instructions for a held-out batch. Its result is independently checked/recorded, then rollback restores baseline in finally while retaining history.

Report statuses include completed, baseline-already-passed, no-change, validation-failed, reuse-failed and error. No-change/error/failure never counts as a successful correction. CLI returns 2 for non-completed live reports, 0 for completed. Progress goes to stderr; JSON report to stdout and outputs/report.json. Normal exceptions are summarized without private native diagnostic text; retained stage explains where it stopped. executor_kind identifies native-codex or injected when set by the module. Four calls maximum; no retry loop. Native execution auth/config semantics remain as documented for reviewer.

Observed live outputs for this constructed example support a narrow corrective-reuse claim only. No general automatic learning, new skill discovery, production routing or Obsidian export is established. User explicitly deferred export until last.

## Pinned public GitHub sources

senai/skills/sources.py imports one explicitly selected public owner/repository package at a required 40-character lowercase SHA-1 commit. No branch/tag fallback, credentials, Git checkout, archive extraction, dependency install or downloaded-code execution. It fetches the exact Git commit and recursive Git tree using unauthenticated GitHub API GETs, verifies their identities, then selects a regular-file subtree (or . for repository root). Package/ancestor symlinks, submodules, malformed/duplicate/traversal paths and incomplete/truncated trees are rejected. Full subtree is preserved, including unreferenced resources; it does not emulate Hermes referenced-file-only selection.

Default transport permits only HTTPS api.github.com/raw.githubusercontent.com, with no credentials/ports/redirects or inherited proxy credentials. It never reads GITHUB_TOKEN/auth files. Per-request socket timeout 20 seconds; no strict total import deadline. Limits: commit metadata 128 KiB, entire recursive tree 4 MiB/50,000 entries, each file 1 MiB, selected package 256 files/8 MiB. Huge repositories can be rejected even for a small selected package. GitHub unauthenticated rate limits/network conditions apply. No automatic retry loop.

Each raw download is addressed by repository+commit+encoded path and checked against declared size and its Git blob SHA-1. Download metadata URLs are ignored. Existing registry SHA-256 covers the full activated package. Skill.source stores the canonical GitHub tree URL containing repository, exact commit and package path; accepted-version/audit timestamps retain import time. Registry restart preserves provenance. No database schema migration needed.

Registry.import_github(repository, *, commit, path, fetch=None) -> Skill injects fetch(url, *, max_bytes) -> bytes for offline tests. After the whole bundle passes source and existing format validation, internal _import_files performs the same atomic package/DB activation as local import. Neither path overwrites conflicting names, including locally revised packages. Ordinary failures before commit leave no active partial import. Crash/orphan-folder limits remain as previously documented.

CLI: import-github OWNER/REPO --commit SHA --path DIRECTORY. Files with executable Git mode are copied as inert ordinary bytes. Validation is structural/integrity checking, not a prompt-injection scanner, permission grant, runtime compatibility proof or endorsement of third-party instructions. Only public GitHub/SHA-1 sources are supported; arbitrary URLs/private repos/archives remain unsupported.

Primary implementation references: https://docs.github.com/en/rest/git/trees and https://docs.github.com/en/rest/repos/contents . Tree modes are used to reject symlinks/submodules rather than trusting content API symlink following.

## Ordinary registry-skill requests

senai/skills/run.py run_request(registry, request, names, *, project, model=None, read_only=False, native_skills=(), executor=None, checker=None, compatibility_check=None) -> RunResult. Select 1-8 distinct saved skill names in this project's registry, validate request/compatibility before invocation, and snapshot their exact packages into a unique run's context/skills/ directories. Registry bytes remain unchanged. Full instruction context max 256 KiB; original request max 32,000 characters.

Uses stable build_prompt for scope/native skill mentions and stable run_codex/CodexOptions for one request. Saved registry instructions are explicit reference context with resource paths, not masqueraded as globally installed native skill names. Optional native_skills produces existing native $mentions. Read-only or workspace-write options apply to a new outputs/skill-runs/<UUID>/workspace; default is workspace-write, approval never, no resume/--last. No shared session mappings/core routes change. Native config/auth/tool behavior applies and sandbox limitations remain as documented.

RunResult fields: id, status, verification, response, workspace, report_path, skills (tuple[RunSkill(name, version, digest, source)]), outcome_ids, error. Retained prompt.txt, response.txt, checks.json and run.json live beside workspace and copied context. The generated artifacts are inside workspace. A successful response without independently observed checks is status completed/verification unverified. Caller checker(response, workspace) -> Iterable[Check] determines explicit checks only. A passing label establishes only those checks, not universal task correctness. Model claims are never parsed into evidence. Outcomes retain a result excerpt up to 64,000 characters; full response stays in run artifacts/report.

Failed checks produce checks-failed/failed; checker exceptions or malformed evidence produce check-error/error with unverified outcomes and preserved response. Execution failures produce execution-error without fabricated successful outcomes. Record persistence failures produce recording-error and retain any already-created outcome IDs. Private exception text is not echoed in reports. CLI returns 2 for these failure statuses; successful unverified runs return 0 with explicit verification unverified.

CLI run NAME REQUEST [--skill ADDITIONAL] [--native-skill INSTALLED] [--model MODEL] [--read-only] [--expect-file RELATIVE_PATH]. --expect-file independently checks only contained regular-file existence, rejects path escapes before execution and treats symlink artifacts as failed. It does not execute arbitrary checker commands or prove generated code semantics.

Outcome storage now resolves supplied digests against accepted_versions rather than assuming the active version is still the one executed. This preserves in-flight identity across another activation. Never-accepted proposals remain rejected. Accepted historical package bytes must remain intact to record evidence. Existing public signatures/data retained; no schema migration.

Real one-shot ordinary CLI QA used the pinned imported skill-creator to generate a local instruction artifact. File presence and separate SKILL.md format/name checks passed. New artifacts are not automatically acquired/activated; provenance/new-skill acceptance is a later explicit step. This is feature-local usability, not coordinator production wiring.

## New locally authored skills and durable origins

senai/skills/learning.py separates creation, checking and acceptance. Registry.stage_learning(run_id, *, path, reason) snapshots a generated package from this project's real outputs/skill-runs/<id>/workspace. It requires a completed source run with observed passed checks and matching recorded source skill/digest/outcome links. Path escapes/symlink ancestors/unsupported packages fail. The source run's check can establish artifact creation only; it never substitutes for candidate behavioral checks. Source report is trusted local state, not a signed attestation or hostile-user security boundary.

LearningCandidate fields: id, name, version, digest, source_run_id, source_path, source_outcome_ids, reason, path, instructions, status, created_at. Candidates remain outside active skills, with status proposed until explicit acceptance. Package bytes and source links persist after restart. Registry.check_learning(candidate_id, *, validator) invokes trusted validator(candidate) -> Iterable[Check]. Empty/malformed results or ordinary checker errors become error, not passed; changed packages cannot reuse a pass. learning_checks(candidate_id) retains all attempts. LearningValidation fields: id, candidate_id, digest, checks, status, error, created_at.

check_with_codex(registry, candidate_id, *, cases, project, model=None, executor=None) is an optional real behavioral checker. Cases are 1-10 objects with name/request/expected_json, total 64,000 characters. Each request uses existing read-only Codex execution, no resume/last, returning JSON that the host compares structurally to expected JSON. Expected answers are not supplied in the model prompt. Model success prose is invalid JSON and fails. Per-case prompts/responses/checks are retained under outputs/learning-evaluations/. No model-produced or downloaded code is executed by the checking harness. Tests prove only supplied cases; native configuration/tool semantics still apply.

Registry.accept_learning(candidate_id) uses common atomic package import with a transactional latest-check gate. Candidate must still be proposed and the newest validation must pass for exact bytes. Candidate acceptance, active/accepted skill records, baseline audit event and learned origin commit together. Duplicate names cannot overwrite an existing skill. New source is run:<source-id>/<relative-package-path>; original generated files stay untouched. Subsequent changes use ordinary versioned revisions/rollback. The baseline audit action remains import for DB compatibility, with reason Accepted learned skill plus the rationale; Origin.kind distinguishes actual learned acceptance from import.

origins table stores name, kind, source_kind, source, source_run_id, linked outcome IDs, reason, original_digest, validation_id and created_at. Origin adds locally_revised from prior activation history; rollback does not erase the fact that a skill was revised here. New local/public imports are imported; new controlled demo imports explicitly use demo=True and are demo. Existing imports are classified from known prior validation/import audit reasons; unknown legacy evidence stays unknown. No wording-based learned inference. Registry.origin(name) and list CLI surface these distinctions without altering immutable Skill fields.

Schema addition: origins, learning_candidates and learning_validations; idempotent migration preserves all old skills/outcomes/revisions/accepted history. Public Origin fields: name, kind, source_kind, source, source_run_id, source_outcome_ids, reason, original_digest, validation_id, created_at, locally_revised. No model weights change. learned_here means an instruction package authored from a local run and accepted against recorded cases, not a guarantee of generalized improvement.
