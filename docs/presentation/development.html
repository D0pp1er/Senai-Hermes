01 / 06Development approach

Small steps.
A connected system.

Senai began with three requirements: accept input, give Codex the right context, and return its output. Memory, messaging, scheduling and skills grew around that working path.

01 User input→02 Senai context→03 Native Codex→04 Retained outcome

The guiding constraint was to keep a usable core while adding small, reviewable features. Native Codex remains the executor; Senai owns the surrounding context, persistence and delivery policy.

Incremental delivery.
Input, execution and packaging came before broader automation.

Independent modules.
Four workstreams developed within explicit ownership boundaries.

One integration point.
Shared routing, dependencies and composition were coordinated on main.

This page summarizes recorded implementation history. It is not an exported development chat, a claim of universal reliability or a new live acceptance report.

04 / 06Architecture and choices

The useful part
is the tradeoff.

The choices below summarize the implementation and documented requirements. Rationale is an architectural explanation, not a claim of a controlled benchmark.

What was chosen, why it fits, and what it costs
ChoiceWhy it fitsTradeoff / limit
Reuse native CodexKeep its models, authentication, tools and native session mechanism.Provider latency and CLI startup remain; supported flags can drift with Codex versions.
Python package + local SQLiteExpose one senai command and durable state without a separate database service.POSIX locks/process handling target WSL; native Windows support is not established.
Project outputs/ boundaryKeep generated artifacts and runtime state separate from harness source.It is a scope policy, not an independent filesystem jail.
Installation-wide human profilesOne owner keeps the same preferences across projects and sessions.This is not a multi-tenant identity system; owners must not be mixed.
Frozen session snapshotsResuming keeps the memory context originally bound to that native UUID.Profile edits need a fresh session; old sessions do not silently refresh.
One shared Telegram conversationMatch the chosen shared-session policy while retaining jobs and history.Paired users share model context/workspace despite private message delivery.
Durable outbox + independent deliverySend saved results after restart without repeating a completed model task.Remote acceptance may be uncertain; exactly-once external effects are not guaranteed.
Confirmation and uncertainty fencesPrevent implicit personal-memory saves, blind retries and unsafe session switches.Some outcomes require explicit human review and recovery.
Explicit skill lifecycleLink exact packages to outcomes, independent checks and accepted history.No automatic activation/weight training; trusted local checks can still be fabricated.
One-way Obsidian exportExpose readable procedures/history while protecting personal and edited notes.No live watcher, bidirectional edit sync or automatic fixture-report export.

05 / 06Lessons from implementation and manual QA

Working code
still needs a usable path.

Manual feedback changed the interface and exposed gaps between module readiness, integration and actual user experience.

01

Repeated configuration belongs in setup

Long venv/project/trust invocations became saved defaults and short commands. Profile edits became memory/user/soul add/show/path.

BEFORERepeated project, installation and trust flags

AFTERsenai chat · senai user add "..."

02

Scheduling should ask, preview and confirm

JSON and offset timestamps remain advanced interfaces. The everyday path asks one field at a time, resolves friendly time and offers only authorized destinations.

BEFOREHand-written JSON and ISO date

AFTERsenai cron create → “tomorrow at 1 am” → preview → yes

03

A merged module is not a connected feature

Adapters still need matching stores, recipients, memory roots, session policies and execution gates. Composition tests verified those seams after each merge.

04

Tests should not inherit the operator’s configuration

An earlier unisolated run loaded local defaults. scripts/test.py now uses disposable configuration and the checkout’s installed command so baseline results are reproducible.

05

Invisible waiting feels like a broken command

Each request still starts Codex execution and normal replies display at completion. An isolated fake-Codex benchmark measured local wrapper overhead near 0.1 seconds; it did not measure the real provider or prove the live latency source.

Visible progress and per-stage live timing remain follow-up work, not shipped performance claims.

06

Documentation needs executable checks too

The four sequence diagrams contained literal semicolons in message labels. Actual Mermaid parsing reproduced four failures; removing the separators made all four pass. Counting diagram blocks had missed the syntax error.

06 / 06Evidence and unfinished work

Show what ran.
Name what didn’t.

A transport test, a provider call and a viewer seeing a photo are different kinds of evidence. The project records them separately.

Recorded evidence

  • Offline suites cover parsing, durable stores, memory confirmation, frozen snapshots, claims, uncertain sends and shared gates.
  • Subprocess fixtures exercise the actual wrapper path without live providers.
  • Earlier live coding/Telegram/media and skills demonstrations are recorded historically in the changelog and workstream handoffs.
  • The 142-case manual checklist gives each current feature a separate Pass / Fail / Not run record.

Limits that remain explicit

  • Live behavior needs each user’s own account, permissions and acceptance checks.
  • Automated success does not guarantee model correctness or exactly-once effects.
  • Research comparison, a complete authentic chat export and final submission-deck acceptance remain separate deliverables.
  • Visual browser acceptance and GitHub deployment must be checked separately; local parser checks do not prove them.
